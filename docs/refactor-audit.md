# Refactor audit — 3 November 2026

## Repository and workflows

This is a Next.js 15 App Router, React 18, TypeScript and Tailwind application. Supabase Auth supplies sessions; PostgreSQL functions and RLS enforce commands and data visibility; private Supabase Storage holds receipts. The client uses a workspace snapshot store and domain clients, with `/api/workspace` and `/api/v1/{iam,master-data,claims,finance,notifications}` as its main API routes. Vercel standalone output and Supabase migrations configure deployment. The bank export adapter writes the existing BIFF8 XLS format from a checked contract and redacted fixture.

An invited user completes onboarding and can submit claims with expense lines and receipts. Claims can be saved as drafts or submitted to direct finance review. Finance officers or administrators other than the submitter or claimant can verify, approve, return for clarification, or reject. Approved claims can be paid individually or selected for a bulk reimbursement batch. Batch export, bank upload recording, transfer reconciliation and disbursement are separate steps; export alone does not mark claims paid. Finance reporting and audit views use the workspace data. The database command function uses row locks, versions and request keys for consequential claim operations.

## Baseline and limits

At audit start: `npm run typecheck` passed; `npm run lint` passed with 129 warnings; `npm test` passed 117 tests in 14 files. No production credentials, claim volume or query plans were used. The prior SQL migrations are historical and must not be edited in place; new SQL changes require a new migration and deployment review.

## Implemented in this pass

- `20261103035921_restrict_payee_bank_details.sql` redacts sensitive payee and non-owner claim fields in both public snapshot RPCs, revokes direct access to the unredacted private snapshots, and enforces payee ownership through additive triggers. It does not rewrite historical rows or the bank export contract. The claim form now limits its payee picker to permitted profiles. This migration **must be reviewed and tested on staging before production rollout**.
- Claim hydration now uses lookup maps and preserves its cached array across unrelated notification updates. This avoids repeated linear searches and attachment scans per claim; no runtime timing comparison is available.
- Claim, dashboard, approval and finance summary totals use integer cents. The database `numeric` and bank XLS adapter were already authoritative and remain unchanged. The added tests cover decimal precision and claim hydration.
- Shared text branding, typography, palette and actions were updated. Sign-in, signup, recovery, onboarding, desktop and mobile navigation, dashboard, claims list, claim form, upload controls, and print branding now use the same presentation. The mobile drawer supports Escape, focus placement, focus containment and scroll lock. The claims list has sorting and 20-row client pagination; this limits rendering but **does not reduce the initial snapshot payload**.
- Unexpected API failures now log operation and error code without logging request payloads or bank details.
- `20261103051032_optimize_invitation_rls.sql` updates the invitation policy without changing who can manage invitations. The local performance advisor warning cleared. `supabase/config.toml` now enables email/password sign-in for invited users under CLI v3 while the global public signup setting remains disabled.

## Verification and remaining measurements

Final local checks: type checking passed; lint passed with 128 warnings (all non-fatal); 120 unit tests passed in 15 files; production build passed. The post-change build reports 482 kB First Load JS for `/claims`, 481 kB for `/dashboard`, and 458 kB for `/login`. No comparable baseline bundle report was retained, so these are **not** claimed as improvements. Chromium checks found no horizontal overflow on sign-in and on eight authenticated routes (`/dashboard`, `/claims`, `/claims/new`, `/approvals`, `/finance/claims`, `/finance/batches`, `/profile`, `/admin/settings`) at 320, 375, 390, 768 or 1280 px. These 40 authenticated route/width checks used a temporary synthetic local admin account that was removed afterward. Visual review of the 320 px dashboard and claim form led to a stacked dashboard filter/action layout and shorter claim form copy; the final dashboard screenshot showed the action fully visible.

The local Supabase stack applied both migrations. `npm run test:backend` then passed 33 assertions, including payee isolation in full and scoped snapshots, concurrent approval/payment checks and receipt isolation. PostgreSQL privilege checks returned `false` for authenticated access to both unredacted private snapshot functions and `true` for the public redacted wrappers. Local security and performance advisors reported no warning-level issues after the invitation policy fix. These are local synthetic-data checks; staging and production behavior remain unverified.

Before deployment, review both migrations on staging and measure representative snapshot size and `EXPLAIN ANALYZE` plans. Server pagination and separate claim detail fetching remain the largest outstanding performance work because existing dashboard, approvals, finance and detail screens all consume the full snapshot contract. The new claims-list pagination only reduces rendered rows. Upload feedback still lacks per-file byte progress and retry; adding those safely requires changing the existing storage upload path. The authenticated browser checks covered navigation, headings and overflow with synthetic data, not a full claim-to-payment interaction or assistive-technology audit. Production data, bank-template compatibility and deployed behavior remain unverified.
